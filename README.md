# Контент по услугам

Каждая карточка MVP хранится в `inc/services.php`. Ниже — расширенная редакционная база для будущих страниц. Все преимущества сформулированы как особенности процесса, без неподтверждённых точностей, сроков и превосходных степеней.

1. **Лазерная резка листового металлопроката с функцией 3D-резки** (`lazernaya-rezka-listovogo-metalla`). Точный раскрой листа по чертежу или 3D-модели, включая пространственную обработку. **Применение:** подготовка деталей к гибке, сварке и сборке. **Изделия:** панели, кронштейны, корпуса, элементы рам. **Преимущества:** сложный контур, повторяемость партии, сокращение последующей обработки. **CTA:** «Рассчитать лазерную резку». **Визуал:** луч над контуром листа или фото резки крупным планом.
2. **Лазерная резка трубного металлопроката с функцией 3D-резки** (`lazernaya-rezka-trub`). Раскрой круглой трубы и профиля с пазами, отверстиями и скосами. **Применение:** точная подготовка сопряжений под сборку. **Изделия:** рамы, фермы, опоры, ограждения. **Преимущества:** совмещение нескольких операций, удобство позиционирования, повторяемая геометрия. **CTA:** «Отправить модель трубы». **Визуал:** профиль с прорезями и размерными линиями.
3. **Изготовление гидрошлангов** (`izgotovlenie-gidravlicheskikh-shlangov`). Сборка РВД под параметры системы и присоединительные размеры. **Применение:** подача рабочей жидкости в подвижных и нагруженных соединениях. **Изделия:** РВД для станков, прессов, спецтехники и линий. **Преимущества:** подбор компонентов по условиям работы, изготовление по образцу или спецификации, проверка сборки. **CTA:** «Подобрать гидрошланг». **Визуал:** рукав с фитингами в разрезе.
4. **Изготовление гидравлических трубок** (`izgotovlenie-gidravlicheskikh-trubok`). Резка, гибка и подготовка жёстких трубопроводов. **Применение:** компактная разводка гидросистем. **Изделия:** магистрали, подводы к цилиндрам, трубные сборки. **Преимущества:** изготовление по схеме, чертежу или образцу; согласование присоединений; готовность к монтажу. **CTA:** «Заказать расчёт трубок». **Визуал:** изометрия гнутой трубки.
5. **Роботизированная сварка серийных изделий** (`robotizirovannaya-svarka`). Сварка повторяющихся узлов по настроенному процессу и оснастке. **Применение:** стабильное производство серий. **Изделия:** кронштейны, рамы, корпуса, сварные узлы. **Преимущества:** воспроизводимая траектория, управляемый цикл, снижение влияния ручных операций. **CTA:** «Оценить серийный проект». **Визуал:** робот-манипулятор и сварочный шов.
6. **Токарные работы** (`tokarnye-raboty`). Обработка деталей вращения по конструкторской документации. **Применение:** получение цилиндрических поверхностей, резьб и посадок. **Изделия:** валы, втулки, оси, фланцы, штуцеры. **Преимущества:** комплекс переходов в согласованной технологии, контроль критичных размеров, работа с единичными и серийными заказами. **CTA:** «Рассчитать токарную деталь». **Визуал:** патрон и контур вала.
7. **Фрезерные работы** (`frezernye-raboty`). Обработка плоскостей, пазов, отверстий и сложных контуров. **Применение:** изготовление корпусных деталей и технологической оснастки. **Изделия:** плиты, корпуса, направляющие, кронштейны. **Преимущества:** обработка по цифровой модели, согласованный контроль размеров, сочетание операций. **CTA:** «Отправить деталь на расчёт». **Визуал:** фреза над координатной сеткой.
8. **Порошковая покраска с фосфатированием** (`poroshkovaya-pokraska-metalla`). Подготовка поверхности методом фосфатирования и нанесение порошкового покрытия. **Применение:** защитно-декоративная отделка металлоизделий. **Изделия:** шкафы, корпуса, рамы, ограждения. **Преимущества:** подготовка поверхности включена в маршрут, равномерное покрытие при технологически подходящей геометрии, выбор цвета по согласованию. **CTA:** «Рассчитать покраску партии». **Визуал:** окрашенная панель и шкала цвета.
9. **Полуавтоматическая сварка мелкосерийных деталей** (`poluavtomaticheskaya-svarka`). Подготовка, сборка и сварка единичных и небольших партий. **Применение:** нестандартные конструкции и проекты с меняющейся номенклатурой. **Изделия:** рамы, опоры, ремонтные детали, корпуса. **Преимущества:** гибкость подготовки, работа по сборочному чертежу, согласование зачистки соединений. **CTA:** «Обсудить сварочную задачу». **Визуал:** маска, горелка и схема шва.
10. **Проверка и испытание гидравлического оборудования** (`ispytanie-gidravlicheskogo-oborudovaniya`). Лабораторная проверка по согласованной программе с фиксацией результатов. **Применение:** подтверждение работоспособности или поиск отклонений. **Изделия:** гидроцилиндры, насосные узлы, арматура, РВД и трубные сборки. **Преимущества:** определённые до начала критерии, контролируемые условия, документирование результата по договорённости. **CTA:** «Согласовать программу испытаний». **Визуал:** манометр и контрольный стенд.

# Рекомендованная архитектура WordPress-темы

```text
zub-industrial/
├── .github/workflows/deploy.yml   # production-деплой
├── assets/css/main.css            # дизайн и адаптивность
├── assets/js/main.js              # мобильное меню и улучшение формы
├── assets/img/                    # оптимизированные локальные изображения
├── blocks/                        # будущие блоки редактора
├── inc/services.php               # Git-версионируемые данные услуг MVP
├── template-parts/                # будущие hero/services/cards/contact
├── style.css                      # обязательный заголовок темы
├── functions.php                  # supports, menus, enqueue, форма
├── front-page.php                 # лендинг
├── header.php / footer.php        # общая оболочка
├── index.php                      # основной fallback
├── page.php / single.php          # страницы и записи
├── archive.php                    # архивы/CPT
└── 404.php                        # ошибка 404
```

Для MVP крупные секции оставлены в `front-page.php`, чтобы запуск был быстрым и правки легко читались в одном PR. При появлении вариантов страниц секции следует без изменения разметки вынести в `template-parts/hero.php`, `services.php`, `service-card.php`, `advantages.php`, `process.php`, `contact.php` и `footer-contacts.php`. `blocks/` нужен только для собственных блоков Gutenberg; `inc/` — для CPT, схемы, SEO и интеграций; `assets/img/` — для WebP/AVIF и SVG, прошедших проверку.

# Как лучше хранить и редактировать контент

| Подход | Сильные стороны | Ограничения | Решение |
|---|---|---|---|
| PHP | быстрый, Git-first, без зависимостей | редактору нужен PR, нет отдельных URL | Использовать в MVP |
| Customizer | встроен в core | неудобен для повторяемых структур, данные в БД | Только логотип/простые настройки |
| ACF | удобные поля и связи | зависимость и лицензирование; значения в БД не попадают в Git | Позже, если нужен редакторский интерфейс |
| CPT `service` | отдельные URL, архив, SEO | нужна миграция контента/БД и шаблоны | Плановый этап 2 |
| Block/FSE | визуальное редактирование | не соответствует лёгкому classic/Git-first MVP | Не выбирать сейчас |
| Hybrid | код задаёт систему, WP хранит публикации | нужно определить источник истины | Лучший долгосрочный вариант |

**Рекомендация:** сейчас — classic theme + массив услуг в `inc/services.php`; контакты и тексты также меняются через Git. На этапе SEO-расширения зарегистрировать CPT `service` в отдельном небольшом functionality-плагине (чтобы контент не исчезал при смене темы), добавить `single-service.php` и `archive-service.php`, а массив использовать как seed/fallback. ACF подключать лишь при реальной необходимости работы контент-менеджера; конфигурацию полей хранить в ACF JSON в Git.

# Git workflow для работы с Codex

- `main` всегда соответствует production; задачи выполняются в `feature/<short-name>` или `fix/<short-name>`. Для маленькой команды достаточно short-lived branches, squash merge и protected `main`.
- Формат коммитов: `feat: add service detail template`, `content: revise hero copy`, `fix: close mobile navigation`, `chore: harden deploy workflow`. Один смысл — один коммит.
- Структуру (`PHP/CSS/JS`) и контент (`inc/services.php`, тексты) менять отдельными коммитами/PR: это упрощает проверку и откат.
- В задаче Codex указывать цель, допустимые файлы, критерии приёмки, запрещённые зависимости и команды проверки. Перед merge просматривать diff, preview/staging, accessibility и результат формы.
- PR: короткое описание, скриншот видимой правки, риски/rollback, список проверок. После review — squash merge. Production workflow запускается только после попадания в `main`.
- Откат: безопаснее `git revert <merge-commit>` и push, чем переписывание истории. При аварии повторно запустить последний успешный workflow либо сделать revert. База данным этим workflow не изменяется.

# Автоматический деплой на WordPress

1. **GitHub Actions + SSH/rsync.** Runner копирует репозиторий в точную папку активной темы. Плюсы: прозрачно, быстро, аудит, `--delete` удаляет устаревшие theme-файлы. Минусы: нужен SSH и аккуратный путь. Использовать по умолчанию. Создать отдельного пользователя/ключ только с доступом к папке темы, защитить Environment, закрепить host key и сделать backup.
2. **DeployHQ / Buddy / Ploi.** SaaS слушает Git и выполняет pipeline. Плюсы: UI, логи, rollback; минусы: цена и ещё одна доверенная сторона. Подходит команде без желания поддерживать Actions. Выдать минимальные права и включить 2FA.
3. **Git на хостинге.** Панель делает pull/hook. Плюсы: мало компонентов; минусы: различия панелей, иногда `.git` оказывается в web-root. Использовать при качественной встроенной реализации; deploy key должен быть read-only.
4. **WP Pusher/аналог.** Плагин получает тему из Git. Плюсы: работает без shell; минусы: runtime-зависимость, токены в WordPress, обновление зависит от сайта. Только если SSH недоступен; ограничить GitHub token одним repo.
5. **SFTP вручную.** Запасной вариант при сбое automation. Плюсы: универсально; минусы: ошибки, нет гарантии полного набора файлов и аудита. Использовать только для восстановления, сверяя release archive/checksum.

**Стартовая рекомендация:** private GitHub repo → PR → `main` → GitHub Actions → SSH/rsync только в `wp-content/themes/zub-industrial/`. До первого deploy создать файловый backup и проверить workflow на staging. `--delete` не должен использоваться с путём `themes/` или `wp-content/`.

# Пример GitHub Actions workflow

Рабочий пример находится в `.github/workflows/deploy.yml`: запуск на push в `main`, ручной повтор, запрет параллельных production-деплоев, валидация `REMOTE_PATH`, исключения и атомарная задержка замен. Нужны repository/environment Secrets:

- `HOST` — hostname без протокола;
- `USERNAME` — отдельный deploy-user;
- `SSH_PRIVATE_KEY` — приватный ключ без passphrase для CI (публичная часть на сервере);
- `PORT` — SSH port, обычно `22`;
- `REMOTE_PATH` — абсолютный путь **до конкретной темы** с `/` в конце.

Вариант с SFTP/password возможен, но ключ SSH предпочтительнее: пароль не нужен в workflow, ключ легко отозвать и ограничить. Секреты никогда не печатать и не добавлять в repo. Для production лучше заменить `ssh-keyscan` на секрет `KNOWN_HOSTS` с заранее проверенным fingerprint.

# Стартовый код темы

Код уже разложен по готовым файлам: метаданные — `style.css`; setup, enqueue и безопасный обработчик формы — `functions.php`; версия контента — `inc/services.php`; семантический лендинг — `front-page.php`; оболочка — `header.php`/`footer.php`; responsive UI — `assets/css/main.css`; доступное мобильное меню — `assets/js/main.js`. Для запуска скопируйте репозиторий как папку `zub-industrial`, активируйте тему, назначьте статическую главную (либо WordPress выберет `front-page.php`) и замените демонстрационные контакты.

Форма использует `wp_mail()`: перед production следует настроить доставку через проверенный SMTP/provider, отправить тест с production-домена и проверить SPF/DKIM/DMARC. Для загрузки чертежей нужен отдельный защищённый механизм: allow-list расширений и MIME, лимит размера, случайные имена, хранение вне публичного доступа, антивирус и политика удаления.

# SEO и аналитика

- Вариант title: **«Металлообработка и изготовление гидравлических узлов — kelrnand»**. Description: **«Лазерная резка листа и труб, токарные и фрезерные работы, сварка, порошковая покраска, изготовление РВД и испытания гидрооборудования.»** Добавить регион только после подтверждения географии.
- Единственный H1 находится в hero; H2 — услуги, отрасли/возможности, качество, процесс, преимущества, контакты; H3 — конкретные карточки.
- Кластеры: `лазерная резка листового металла`, `лазерная резка труб`, `изготовление РВД`, `гидравлические трубки`, `роботизированная сварка`, `токарные работы`, `фрезерные работы`, `порошковая покраска с фосфатированием`, `испытание гидрооборудования`. Не перечислять их искусственно.
- Ссылки-якоря имеют понятные названия; после появления страниц карточки должны ссылаться на canonical URL услуги, а не только на `#contact`.
- Schema.org: `Organization`/более точный фактический подтип, `WebSite`, `BreadcrumbList`; на страницах услуг — `Service` с `provider`. Не добавлять неподтверждённые `Review`, рейтинг, цены или географию. JSON-LD держать в одном модуле или SEO-плагине, не дублировать.
- Добавить OG/Twitter title, description, canonical и изображение 1200×630; sitemap/robots; Search Console/Вебмастер. Analytics/Метрика — только после настройки consent по применимым требованиям, события `form_start`, `form_success`, `phone_click`, `email_click` без персональных данных.
- Изображения: AVIF/WebP с размерами, lazy loading ниже первого экрана; hero не должен блокировать LCP. Alt описывает функцию/содержание (`«Лазерная резка профильной трубы»`), декоративный элемент имеет `alt=""`; не набивать alt ключами.
- В будущем каждой услуге дать уникальные title/H1/description, параметры и ограничения, процесс, FAQ, реальные кейсы, изображения, перелинковку и CTA. Добавить страницы отраслей, кейсов и статей; настроить breadcrumbs, canonical и редиректы со старых slug.

# Безопасность и обслуживание

- [ ] Ни ключи, ни пароли, ни `.env`, ни `wp-config.php` не находятся в Git; Secrets защищены Environment.
- [ ] Deploy-user имеет минимальный доступ только к теме; ключ можно быстро отозвать; host key проверен.
- [ ] Перед deploy есть проверяемый backup файлов **и БД**, а восстановление протестировано.
- [ ] Core, PHP и необходимые плагины обновляются сначала на staging; неиспользуемые темы/плагины удалены.
- [ ] Сильные уникальные пароли, 2FA, rate limiting; администраторов минимум.
- [ ] `DISALLOW_FILE_EDIT` включён в `wp-config.php`; production debug-display выключен, логи недоступны из web.
- [ ] Права обычно 755 для каталогов и 644 для файлов (уточнить у хостинга); PHP не может произвольно писать в theme directory.
- [ ] Форма защищена nonce/honeypot; дополнительно нужны rate limiting, SMTP и privacy notice; входные данные никогда не доверяются.
- [ ] Staging изолирован от индексации и production-данных; ветка/Environment staging используется до production.

# Чеклист запуска

1. Заменить название, телефон, email, адрес, реквизиты и политику; проверить все ссылки и согласие.
2. Добавить реальные подтверждённые возможности оборудования, материалы, форматы файлов, географию и сроки — не придумывать числа.
3. Оптимизировать логотип, favicon, OG и производственные фото; получить права на материалы.
4. Проверить PHP syntax, WordPress Coding Standards, отсутствие JS ошибок, 360/768/1440 px, Chrome/Firefox/Safari.
5. Пройти страницу клавиатурой и screen reader smoke-test; проверить contrast, focus, labels и reduced motion.
6. Настроить SMTP, SPF/DKIM/DMARC; проверить успех/ошибку формы и доставку без персональных данных в analytics/logs.
7. Установить HTTPS, production permalink, title/meta/canonical/OG/schema, sitemap и панели вебмастеров.
8. Сделать backup и staging deploy; сверить `REMOTE_PATH`; затем merge в `main`, проверить Actions и production smoke-test.
9. Зафиксировать ответственного за обновления, backup restore, заявки и ежемесячную проверку формы.

# Примеры задач для Codex

- **Карточка:** «Создай ветку `content/add-bending`. Добавь услугу гибки в `inc/services.php` после лазерной резки. Не меняй CSS. Используй подтверждённый текст ниже, уникальный slug и CTA; выполни `php -l` для всех PHP-файлов и покажи diff».
- **Hero:** «Перепиши только видимый текст hero в `front-page.php` под аудиторию производителей спецтехники. Сохрани H1, две CTA, факты, HTML и нейтральные B2B-формулировки; не добавляй неподтверждённые цифры».
- **Страница резки:** «Добавь `single-service.php` и reusable template parts для страницы лазерной резки. Сохрани стили landing, breadcrumbs, Service JSON-LD без rating/price и CTA. Не регистрируй CPT в теме — подготовь отдельный functionality plugin».
- **Мобильное меню:** «Улучши меню: Escape закрывает, focus возвращается на toggle, resize снимает mobile state. Не добавляй библиотек; проверь keyboard navigation и reduced motion».
- **Schema:** «Добавь `inc/schema.php` с валидным JSON-LD Organization и WebSite. Все реквизиты возьми только из переданного объекта конфигурации, экранируй вывод, не дублируй schema SEO-плагина; добавь тест JSON parse».
- **Форма:** «Измени форму на двухколоночную при ≥768 px, сохрани labels, nonce, honeypot и server validation. Не логируй пользовательские данные; приложи desktop/mobile screenshot со staging».
- **Откат:** «Найди merge-коммит изменения формы, создай revert без переписывания истории, выполни smoke-check и не затрагивай последующие контентные коммиты».

Итоговый пакет включает архитектуру и готовый лендинг, версионируемый контент десяти услуг, расширяемые WordPress-шаблоны, Git/PR-процесс, безопасный deployment scaffold, SEO-план и launch/security checklist. MVP не зависит от page builder или ACF; следующий логичный этап — реальные данные компании, фото, staging и CPT услуг для отдельных SEO-страниц.
